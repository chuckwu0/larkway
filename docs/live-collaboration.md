# 长任务中的实时协作

## 产品分工

话题承载即时提问、解释、授权、纠正、选择和验收讨论；关联的飞书任务承载长期进展、里程碑、阻塞、待验收和结案。原生 runtime 的一个 turn 只是一次执行，可能包含很多次模型请求与工具调用。

三种事实分别维护：

| 事实 | 来源 | 不代表 |
| --- | --- | --- |
| 消息已交给当前执行 | 原生输入回执 | Agent 已处理或认可授权范围 |
| 本轮已结束 | runtime 结束事件 | 整个需求已完成 |
| 任务已验收/关闭 | 人工确认及既有任务工作流 | 上一条工具命令退出成功 |

任务创建、里程碑判断和人工验收仍由 Agent 及其工作流负责。bridge 不分析文本来选择业务流程，也不把工具事件或每条过程回复复制为任务评论。

## 运行中输入

支持输入能力的 `RunHandle` 提供可选 `steer(prompt)`。当前 Codex 冷启动与热池实现原生 `turn/steer`，使用当前原生 thread 和 expectedTurnId，不另开 turn、session 或子进程。原轮次的总预算不重置。

入站继续经过原有 transport 的身份/触发/去重规则。handler 在工作并发槽之外按 session 顺序交付补充消息；只有同 bot、相同 canonical session 和 chat 的活跃 handle 可以接收。quote reply 的 queue key 可能宽于 session key，不能只凭 queue key 插话。

原文、发送者、消息标识、引用、文档与附件指针随追加输入保留。不判断它是“授权”还是“变更”，也不向不同发送者扩大发言权限。

| 交付结果 | 行为 |
| --- | --- |
| accepted，且回执匹配预期 turn | 归入当前执行，给用户接收回执，不再次排队 |
| 明确未接收、尚未启动、已结束或不支持 | 转入既有串行队列；需要等待时显示排队回执 |
| 超时、断连、写入异常或回执不匹配 | 标记交付待核对，不自动重发 |

每条可能被追加的输入先写 `_input-deliveries/<bot>/<message-hash>.json`，位于配置的 session 根目录下。`sending` 在发送前落盘；`accepted`/`unknown` 和崩溃留下的 `sending` 均禁止自动重放。明确 `rejected` 可以正常排队。该文件仅记录传输事实，不是业务任务账本。

结果不明时由维护者结合飞书原消息、日志中的 native thread/turn 与原生历史核对；当前不提供自动推断或自动重新提交。文件仅本机私有保存，含用户输入，应遵循 session 数据管理规则。

`/stop` 沿用带外停止，停止前已收到但尚未交付的补充不会在停止后自行启动新轮次。停止无法撤回已经被原生执行采用的输入。

普通话题输入不等于原生审批响应。原生 `tool/requestUserInput` 和审批挂起请求仍需要对应协议的 requestId；本功能不宣称补齐这些往返能力。其他后端未提供 steer 时保持排队。

协议参考：[Codex App Server](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)。实际 CLI 版本仍需隔离验证，不能仅凭文档认为某部署已通过。

## 过程回复与最终结论

Codex 明确 `phase=commentary` 的完成消息映射为带 itemId 的 `progress_message`。其完整段落立即进入主回复卡的“过程回复”，无需等 turn 结束。只有明确 final phase 的内容进入最终答案 buffer；未知 phase、reasoning、工具参数和工具原始结果不经此通道展示。

第一版以 `item/completed` 为过程段落的权威快照，不展示尚未完成段落的 token delta。相同 item 去重；阶段回复不会触发执行结束、释放 session 锁或自动勾完任务。

CardKit 与 legacy 卡都展示过程区，最终结论与之分开。无 final 的正常轮次保留过程内容，说明“本轮已结束，未提供最终结论”，不自动把最后一条进展当结论。

完整过程写入本 session 的 `.larkway/progress-<trigger>.json`。为避免超过卡片容量，超过 6 KB 的历史按段发到原话题并从主卡链接；平台返回消息深链时，每段含前一段的真实链接，主卡保留最近链接和最新一段；没有深链时明确提示在原话题查看分段历史，不编造消息链接，也不逐条刷群。稳定内容摘要作为发送幂等键。没有 post 能力或归档失败时明确标注未投递，完整记录继续保留在本机，不假称用户已经看到。

CardKit `firstVisibleReplyAt` 记录首次成功提交可见回复的时间；`firstAnswerAt` 仍只表示最终答案事件，不能用接收回执或过程事件改善最终答案耗时数字。

## 选择与状态

新生成的选择按钮携带 question/options 的稳定版本。handler 在最终卡片发布前保存本 session 的 `decision.json`；旧版本或已经没有有效选择的按钮被拒绝，提示查看最新回复。解释 A/B 不等于已选择；仍声明的相同问题可以跨轮次保留。

结束标题默认“本轮已结束”，已有 Agent 明确声明的进行中、错误和自定义标题仍保留。业务验收状态由 Agent 或任务工作流提供，bridge 不根据 exitCode 0、choice 存在或文字措辞推断。飞书原生进度气泡的固定系统文案可能仍显示“任务已完成”，不能据此判定关联业务任务已验收。

## 任务与通知

既有任务同步路径继续运行；同一任务只能选定一条维护链路，禁止与独立任务工具同时双写旧 task-handle 声明。

Agent 在长轮次内可以发布实质里程碑、阻塞、需要人行动或阶段交付的任务评论，无需等 final。消息被采用后如何调整业务状态由 Agent 判断；同一里程碑使用稳定事件键去重。评论成功不等于手机推送已送达。

话题与任务保留真实回链。采用自定义任务工具的部署，其身份与权限沿用既有配置，不因实时输入改用个人身份或扩大 scopes。需要人工验收的任务保留原结案规则，runtime 不自动关闭。

## 验证与发布

协议 fixture / mock 测试覆盖过程与 final 分离、热池/冷启动输入、接收/拒绝/未知回执、跨 session、停止和完成竞态、长历史与卡片降级。独立真实 runtime 验证输入是否进入模型并被采用；测试话题验证可见回复和任务评论。遵守 [runtime validation](runtime-validation.md)，不把网络或子进程加入单元测试。

部署验收须分别记录代码验证、原生执行验证和飞书送达验证，不能相互替代。回滚保留输入交付记录、session 和任务映射；已接收或结果不明的输入不能重新排队。升级仍应等待安全窗口，不能为了发布中断用户的活跃工作。

同一候选版本可分别设置 `LARKWAY_LIVE_INPUT=off` 恢复队列模式、`LARKWAY_PROGRESS_REPLIES=off` 关闭新增过程展示。输入开关关闭后仍核对已存在的交付记录，避免把已接收或结果不明的输入再排队。不要在有未核对的交付记录时直接恢复不认识该记录的旧二进制；先核对原生及入站去重状态。
