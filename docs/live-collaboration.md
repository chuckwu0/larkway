# 长任务中的实时协作

## 产品分工

话题承载即时提问、解释、授权、纠正、选择和验收讨论；关联的飞书任务承载长期进展、里程碑、阻塞、待验收和结案。原生 runtime 的一个 turn 只是一次执行，可能包含很多次模型请求与工具调用。

三种事实分别维护：

这些是日志与工作流的事实边界，不是给用户展示的三个状态区块。卡片以当前答复为主，不播报内部执行结构。

| 事实 | 来源 | 不代表 |
| --- | --- | --- |
| 消息已交给当前执行 | 原生输入回执 | Agent 已处理或认可授权范围 |
| 本轮已结束 | runtime 结束事件 | 整个需求已完成 |
| 任务已验收/关闭 | 人工确认及既有任务工作流 | 上一条工具命令退出成功 |

任务创建、里程碑判断和人工验收仍由 Agent 及其工作流负责。bridge 不分析文本来选择业务流程，也不把工具事件或每条过程回复复制为任务评论。

## 运行中输入

支持输入能力的 `RunHandle` 提供可选 `steer(prompt)`。当前 Codex 冷启动与热池实现原生 `turn/steer`，使用当前原生 thread 和 expectedTurnId，不另开 turn、session 或子进程。原轮次的总预算不重置。

入站继续经过原有 transport 的身份/触发/去重规则。handler 在工作并发槽之外按 session 顺序交付补充消息；只有同 bot、相同 canonical session 和 chat 的活跃 handle 可以接收。quote reply 的 queue key 可能宽于 session key，不能只凭 queue key 插话。

原文、发送者、消息标识、引用、文档与附件指针随追加输入保留。不判断它是“授权”还是“变更”，也不向不同发送者扩大发言权限。

| 交付结果 | 行为 |
| --- | --- |
| accepted，且回执匹配预期 turn | 静默归入当前执行，不额外发接收状态消息、不再次排队 |
| 明确未接收、尚未启动、已结束或不支持 | 转入既有串行队列，沿用处理表情，不额外发排队状态消息 |
| 超时、断连、写入异常或回执不匹配 | 记录待核对，不自动重发；给用户简短异常提示和下一步 |

每条可能被追加的输入先写 `_input-deliveries/<bot>/<message-hash>.json`，位于配置的 session 根目录下。`sending` 在发送前落盘；`accepted`/`unknown` 和崩溃留下的 `sending` 均禁止自动重放。明确 `rejected` 可以正常排队。该文件仅记录传输事实，不是业务任务账本。

结果不明时由维护者结合飞书原消息、日志中的 native thread/turn 与原生历史核对；当前不提供自动推断或自动重新提交。文件仅本机私有保存，含用户输入，应遵循 session 数据管理规则。

`/stop` 沿用带外停止，停止前已收到但尚未交付的补充不会在停止后自行启动新轮次。停止无法撤回已经被原生执行采用的输入。

普通话题输入不等于原生审批响应。原生 `tool/requestUserInput` 和审批挂起请求仍需要对应协议的 requestId；本功能不宣称补齐这些往返能力。其他后端未提供 steer 时保持排队。

协议参考：[Codex App Server](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)。实际 CLI 版本仍需隔离验证，不能仅凭文档认为某部署已通过。

## 三种输出各有职责

同一 bot 在同一话题的一次活跃执行只保留一张主任务卡。运行中输入交给该执行，不另起轮次或卡片；跨话题的并发不受影响。

| 输出 | 用途 | 更新时机 |
| --- | --- | --- |
| 主任务卡 | 工具计数、简短当前进展，交付时原卡转为结论 | 工具计数独立更新；摘要仅在实质变化时更新 |
| 话题普通消息 | 回答追问、主动补充重要信息、真实 @ 需要行动的人 | Agent 按沟通需要发送新消息，明确对应输入或事项 |
| 关联飞书任务 | 关键里程碑、阻塞、待办人、交付与通知 | 沿用既有任务工具及稳定事件键，不逐条复制工具活动和问答 |

### 主卡当前进展

Agent 原子写本 session 的 `.larkway/state.json`，显式声明当前卡片的摘要：

```json
{
  "status": "in_progress",
  "card_progress": {
    "message_id": "本轮主任务卡的触发消息 ID",
    "text": "身份切换已验证，搜索返回仍在验证。"
  }
}
```

bridge 只接受 `message_id` 与当前主卡触发消息精确匹配的声明，正文最多 2,000 字符；没有匹配声明时保留已有摘要。无效/暂时未写完的文件不会清空已显示内容，重复文本不会重新提交。摘要用原子元素替换，不重放打字动画。工具计数沿用原设计独立刷新；真正的最终答案仍可流式生成，最后在原卡收尾。

普通原生 commentary、reasoning、工具参数和结果都不自动成为主卡正文。它们保留在原生运行记录中；bridge 不生成用户侧过程历史、折叠历史或“较早回复”分段消息。已有的本机历史文件不会因升级被删除。

### 普通消息

普通消息是一条独立沟通，不是第二个任务。Agent 使用现有 `lark-cli`、本 bot 身份和已有权限发送；收到运行中输入时，prompt 提供该输入的精确 `message_id` 和回复命令指针。使用 `--reply-in-thread` 留在原话题，稳定 `--idempotency-key` 防止重复；需要通知某人时使用真实 at 标签，不能用卡片内视觉 @ 或纯文字 @ 冒充通知。

追问答复发出后保持可读，不被后续进展改写；追问答完不会结束原执行或主卡。主动重要补充、需要确认/提供材料的事项也可以发普通消息，是否发送由 Agent 判断。bridge 不根据文字关键词推断业务意图，也不把所有 commentary 改成普通消息。发送结果不明时核对已有消息，不换请求键盲重试。

`response_surface.post.mentions` 仍只表达卡片中的视觉提及；不能用它替代上述真实消息。bridge 的 post 开关只控制 bridge 自身的出站路径，不能当作对 Agent 原生 CLI 工具的权限隔离。

### 兼容与结论

最终答复仍以原生 final 通道或已有答案 marker 为准；卡片交付不代表飞书任务已验收。需要人工确认时结论准确说明未决事项，不自动勾完任务。

已有原生会话升级时，仅补发一次新输出契约，保留原 session/history，不重开会话；后续继续增量 prompt。其他后端尚无运行中输入能力时仍按原队列处理，不宣称已具备 Codex 的实时插话能力。

CardKit `firstVisibleReplyAt` 记录首次成功提交可见正文的时间，`firstAnswerAt` 仍只表示最终答案事件；普通消息的实际送达需要独立回读，不能用原生输入 accepted 替代回复送达。

## 选择与状态

新生成的选择按钮携带 question/options 的稳定版本。handler 在最终卡片发布前保存本 session 的 `decision.json`；旧版本或已经没有有效选择的按钮被拒绝，提示查看最新回复。解释 A/B 不等于已选择；仍声明的相同问题可以跨轮次保留。

普通最终卡片不添加“本轮已结束”等执行状态标题，也不添加“本轮结果”等分区。Agent 的业务内容、自定义标题及需要人行动的异常仍保留。业务验收状态由 Agent 或任务工作流提供，bridge 不根据 exitCode 0、choice 存在或文字措辞推断。飞书原生进度气泡的固定系统文案可能仍显示“任务已完成”，主卡不再重复一份执行完成提示。

## 任务与通知

既有任务同步路径继续运行；同一任务只能选定一条维护链路，禁止与独立任务工具同时双写旧 task-handle 声明。

Agent 在长轮次内可以发布实质里程碑、阻塞、需要人行动或阶段交付的任务评论，无需等 final。消息被采用后如何调整业务状态由 Agent 判断；同一里程碑使用稳定事件键去重。评论成功不等于手机推送已送达。

话题与任务保留真实回链。采用自定义任务工具的部署，其身份与权限沿用既有配置，不因实时输入改用个人身份或扩大 scopes。需要人工验收的任务保留原结案规则，runtime 不自动关闭。

## 验证与发布

协议 fixture / mock 测试覆盖显式进展与 final 分离、热池/冷启动输入、接收/拒绝/未知回执、跨 session、停止和完成竞态、无历史补发及卡片降级。独立真实 runtime 验证输入是否进入模型并被采用；测试话题验证同一进行中主卡、追问的独立普通回复、主动补充与真实 @，以及既有任务评论。长任务应连续输出多条相近的普通 commentary，验证它们不会刷新正文或触发历史补发。遵守 [runtime validation](runtime-validation.md)，不把网络或子进程加入单元测试。

部署验收须分别记录代码验证、原生执行验证和飞书送达验证，不能相互替代。回滚保留输入交付记录、session 和任务映射；已接收或结果不明的输入不能重新排队。升级仍应等待安全窗口，不能为了发布中断用户的活跃工作。

同一候选版本可分别设置 `LARKWAY_LIVE_INPUT=off` 恢复队列模式、`LARKWAY_PROGRESS_REPLIES=off` 关闭新增过程展示。输入开关关闭后仍核对已存在的交付记录，避免把已接收或结果不明的输入再排队。不要在有未核对的交付记录时直接恢复不认识该记录的旧二进制；先核对原生及入站去重状态。
